Recommended Approach: Detailed Steps

Migrating a DSM 2.2.3 database (Aria Automation integration) to VCF-native DSM 9.1.1

Summary: The customer upgrades VCF to 9.1.1 without upgrading the existing DSM 2.2.3 instance. After the VCF upgrade, they move the existing database to a new VCF-native DSM 9.1.1 deployment by using PostgreSQL replication (Disaster Recovery).

Starting point: VCF 5.2 with Aria Automation, which is integrated with DSM 2.2.3. DSM runs one PostgreSQL 16.8 database (16.8+vmware.v2.2.1).

Prerequisite: Confirm that the customer is willing to adopt the new VCF Automation (VCFA) native tenancy model on VCFA 9.1.1. This approach only works with that model, because DSM integrates with VCFA through native tenant organizations only. Legacy tenants that are moved into VM Apps organizations can't be used for the DSM database migration.

Assumption: The rest of these steps assume that the customer adopts the VCFA native tenancy model after the upgrade to VCF 9.1.1.

Downtime: Application downtime starts when client connections to the existing database are blocked (step 10) and ends when the applications are switched to the new primary (step 12). Plan a maintenance window for this.

Phase 1: Before the VCF Upgrade

Recommended (optional): Before you upgrade VCF, enable backups on the existing PostgreSQL database if they aren't enabled already. This isn't required for the migration, but it gives you a recovery point if something goes wrong during the upgrade or the migration.

  1. Enable replication on the existing PostgreSQL database (16.8+vmware.v2.2.1) through Aria Automation, and note the replication connection string. Important: Only enable replication. Don't create a replica at this stage.
  2. As the DSM admin, get the CA certificate of the existing PostgreSQL database from the VMware Data Services Manager UI. The read replica created after the upgrade needs this certificate to trust the source database.
  3. Upgrade VCF 5.2 to VCF 9.1.1 without upgrading DSM.

Phase 2: After the Upgrade to VCF 9.1.1, Set Up the New DSM

  1. Install a new DSM 9.1.1 as a VCF-native deployment.
  2. As the VCFA provider admin, assign a dedicated provider organization.
  3. Log in to the standalone DSM UI as the DSM admin, and enable the PostgreSQL 16.14 9.1.1 data service version.
  4. As the VCFA provider admin, create a data services policy (DSP) for PostgreSQL.

Phase 3: Migrate the Database

  1. As a tenant admin or user, create a PostgreSQL read replica instance using version 16.14 via Data Services Manager in VCF Automation. In the Data Availability and Protection step:
    1. Change the scheme of the replication user connection string that you noted in step 1 from postgres://<connection-string> to postgresql://<connection-string>.
    2. Under Certificate Trust Source, select Custom CA.
    3. Paste the PEM-formatted CA certificate of the primary database from step 2.
  2. Confirm that the read replica is in sync with the primary and that replication lag is close to zero. You can check the replication lag on the primary instance in the DSM 2.2.3 standalone UI, on the database's Summary page, in the Data Availability and Remote Replication section.
  3. Block client connections to the existing PostgreSQL database.
  4. Promote the read replica to primary.
  5. Switch the application connections from the old instance to the new primary database instance.
  6. Verify that the applications can connect and work against the new database.

Phase 4: Cleanup

Do these steps only after the new database has been validated.

  1. Delete the old PostgreSQL database by using the DSM API.
  2. Delete the old DSM 2.2.3 instance from vCenter.
